# Git for Unity

`ru.lev.unity-git` — git внутри редактора Unity. Открывается: **Window → Git**,
настройки: **Edit → Project Settings → Git**.

[English version](README.md)

Пакет не пытается заменить git-клиент для кода. Он делает то, что умеет только
редактор: знает, что `Foo.cs` и `Foo.cs.meta` — одна сущность, видит сцену
объектами и компонентами, а не строками YAML, и понимает, что смена ветки
утянет за собой переимпорт.

Работает с любым git-сервером. Возможности хостинга — merge request'ы, задачи,
ревью — подключаются **интеграциями**; первая из них — GitLab.

## Требования

* Unity 6000.0 или новее (проверено на 6000.3)
* `git` в PATH; для локов и LFS — `git-lfs`
* Для интеграции GitLab — токен API с правом `api`

## Установка

* **Asset Store:** добавь пакет в свои ассеты и импортируй из Package Manager → My Assets.
* **Git URL:** Package Manager → **+** → **Add package from git URL…** и адрес
  `https://github.com/LatyninEugene/git-for-unity.git?path=/Packages/ru.lev.unity-git`.
  Чтобы закрепить версию, допиши `#v1.0.0-alpha.1`.
* **.unitypackage:** Assets → Import Package → Custom Package…. Пакет встаёт встроенным
  пакетом в `Packages/ru.lev.unity-git` и виден в Package Manager, пример — на его вкладке
  Samples.

## С чего начать

1. Открой проект, лежащий в git-репозитории, и выбери **Window → Git**.
2. На вкладке «Изменения» отметь файлы, фрагменты или строки, напиши сообщение и закоммить.
   Pull, Push и Fetch — в шапке окна.
3. Выбери в списке сцену, префаб или любой ассет — изменения видны объектами, в инспекторе
   или картинкой.
4. Правой кнопкой по ассету в окне Project → **Git** — история и локи.
5. Если проект на GitLab, включи интеграцию в **Project Settings → Git**.

## Что умеет ядро

* **Статус в окне Project.** Метка поверх иконки ассета: `M` изменён, `A` добавлен,
  `?` новый, `D` удалён, `R` переименован, `!` конфликт. Ассет и его `.meta` — одна метка.
* **Изменения и коммит.** Дерево изменений, флажки на файлах, фрагментах и строках,
  diff с подсветкой изменённой части строки, исправление последнего коммита, проверки
  перед коммитом: ассет без меты, дубли GUID, ссылки на то, что не уйдёт в коммит,
  крупный файл мимо LFS, указатель LFS вместо файла.
* **Сцены и префабы объектами.** Семантический diff по `fileID`: какой объект
  добавлен, какой компонент изменён, какое свойство поехало. Метки изменений в
  иерархии и инспекторе, окно «было и стало» с возвратом значений.
* **Превью ассетов.** Каждая версия ассета показывается так, как он выглядит: текстуры,
  материалы, меши и модели, звук, анимации, Timeline, префабы, настройки сцены.
  Вкладки «Вид», «Инспектор», «Изменения», «Объекты», «Текст»; сравнение рядом,
  шторкой, переключением, наложением и разницей.
* **История и ветки.** Журнал с графом, фильтры, действия с коммитами, безопасное
  переключение веток, история файла и ассета.
* **История объектов.** Кто, когда и в каком коммите менял сцену, объект или
  компонент — из контекстного меню иерархии и инспектора.
* **Конфликты.** Слияние сцен и префабов по объектам и свойствам: иерархия и
  инспектор в три колонки — моё, итог, их; проверка итога перед записью,
  резервные копии в `Library/LevGit/MergeBackups`. Текстовые файлы — прямо в окне,
  бинарники — версией целиком.
* **LFS и локи.** Замки на ассетах в Project, иерархии и инспекторе; взятие и
  снятие из контекстного меню с проверкой свежести; перехват сохранения чужого
  залоченного файла; автолок; настройка `lockable`; докачка нескачанного из LFS.
* **Восстановление push.** Если сервер отклонил push из-за разошедшейся истории (например,
  после исправления последнего коммита), окно объясняет причину и предлагает
  `push --force-with-lease` после свежего fetch; защищённая ветка так и называется.
* **Консоль.** Каждая команда git, которую выполняет пакет, — с выводом, кодом выхода и
  длительностью, и строка для своих команд git. У push, pull, fetch, clone и ls-remote консоль
  показывает **этапы** по трассировке самого git (trace2): хуки, ssh, упаковка — когда начался
  каждый и сколько длился. Этапы упавших и долгих команд попадают также в журнал и отчёт о проблеме.

## Язык

Интерфейс есть на английском и русском, по умолчанию — на языке системы. Сменить:
**Preferences → Git → Язык** или меню **⋮** окна Git — окна переключаются сразу, без
перезапуска. Пункты меню Unity остаются на английском.

Переводы — файлы gettext в `Editor/Localization/<язык>.po`. Чтобы добавить язык, собери
шаблон командой `python "Tools~/localization.py" pot template.pot`, переведи его и сохрани
как `Editor/Localization/<код>.po`.

## Сообщить о проблеме

**Help → Git for Unity → Report a Problem…** (то же — в меню окна Git и рядом с ошибкой
в строке состояния) собирает zip-файл с диагностическими данными:

* версии Unity, ОС, git и git-lfs, важные настройки git;
* сводку репозитория — ветка, число изменений и конфликтов, локи — без содержимого файлов;
* настройки пакета без адресов серверов;
* нашёл ли пакет внутренние механизмы Unity, на которые опирается;
* последние предупреждения, ошибки и команды git, журнал пакета за выбранные дни.

Отчёт можно изучить самостоятельно или приложить к
[issue на GitHub](https://github.com/LatyninEugene/git-for-unity/issues/new/choose). Автоматически он никуда не отправляется.
Токены, пароли и учётные данные в адресах вычищаются всегда. Пути к файлам, имена
веток и адрес сервера можно скрыть. Текст отчёта виден до сохранения.

Если проблему трудно поймать, включи **Подробный журнал** в окне отчёта, повтори проблему
и сохрани отчёт. Журнал пакета лежит в `Library/LevGit/Logs` и хранится 7 дней
(**Help → Git for Unity → Open Log Folder**).

## Интеграции

**Project Settings → Git → Интеграции** — у каждой интеграции флажок и своя
страница настроек. Выключенная интеграция не показывает вкладку и не обращается
к серверу. Если remote проекта похож на сервер интеграции, страница предложит её
включить.

Интеграция — класс, реализующий `Lev.Git.IGitIntegration`, в своей сборке поверх
`Lev.Git.Editor`. Ядро находит её само через `TypeCache` и берёт от неё только
то, что она умеет: веб-адреса коммита и ветки, страницу SSH-ключей, страницу
создания токена, свою вкладку в окне.

Необязательные возможности:

* `IGitBranchBadges` — значки у веток в журнале (у GitLab — открытый MR);
* `DiffView.LineMenu`, `ObjectMenu`, `LineNote`, `ObjectNote` — пункты меню и
  пометки у строк diff и объектов сцены: так вкладка интеграции вешает на
  изменения комментарии ревью;
* пункты «Открыть в …» у коммита и ветки появляются сами, если интеграция
  отдаёт `CommitUrl` и `BranchUrl`.

### GitLab

**Project Settings → Git → GitLab.**

* **Сервер.** Адрес инстанса и путь проекта выводятся из git remote, но их можно
  задать вручную — например, если remote работает по SSH. Хранятся в
  `ProjectSettings/LevGitGitLabSettings.asset` и коммитятся.
* **Токен API — отдельный** от учётных данных git для push: отзыв одного не ломает
  другое. Токен хранится только в системном хранилище учётных данных этой машины
  (на Windows — Диспетчер учётных данных, на Linux — Secret Service), не в проекте и
  не в журнале. Со страницы его можно задать или заменить (сохраняется после проверки
  на сервере), создать в GitLab с заполненным названием и правами, проверить
  пользователя, права и срок, выпустить новый взамен через API, удалить с этого
  компьютера или отозвать.
* **Рабочий процесс** — настройкой проекта, а не решением пакета: кто может
  слить из редактора, что делать после слияния, шаблон имени ветки из задачи
  (`{iid}`, `{title}`), от чего её отводить, целевая ветка, draft, squash и описание
  нового MR, отборы списков по умолчанию.

**Вкладка GitLab** в окне Git — переключателем «Merge request'ы | Задачи».

* **Merge request'ы.** Отбор: мои, ждут моего ревью, все открытые, слитые,
  закрытые. Карточка: можно ли слить и почему нет, одобрения, пайплайн.
  Действия: перейти на ветку, слить или «слить, когда пайплайн пройдёт»,
  rebase на сервере, draft, одобрить, закрыть. Создание MR из текущей ветки.
* **Изменения MR** — в том же виде, что вкладка «Изменения»: дерево, превью,
  diff, сцены объектами. Правой кнопкой по строке — комментарий к строке, по
  объекту или компоненту сцены — комментарий к объекту. В GitLab комментарий к
  объекту лежит у строки этого объекта в YAML сцены и виден в браузере; в
  редакторе он снова находит объект по fileID.
* **Обсуждения** — общий комментарий, ответы, «решить» и «открыть снова»,
  переход к строке или объекту в изменениях.
* **Задачи.** Отбор: назначенные мне, созданные мной, все открытые, закрытые.
  «Начать работу» создаёт ветку по шаблону проекта или переходит на уже
  заведённую и при желании назначает задачу на себя. На ветке задачи —
  «Создать MR…» с `Closes #N`. Новая задача — со снимком окна Game или Scene.
* **В журнале** у веток с открытым MR — значок «!12»; щелчок открывает MR во вкладке.

GitLab по HTTP поддерживается для локальных сетей. Токен в этом случае передаётся
незашифрованным — пакет это не запрещает, но токен никогда не пишет в журнал и отчёт.

## Настройки ядра

`ProjectSettings/LevGitSettings.asset`, коммитится, секретов не содержит.

| Настройка | По умолчанию |
|---|---|
| Основной remote | `origin` |
| Выбирать отдельные строки | выключено |
| Изменения сцены в иерархии | включено |
| Кто менял объект — в инспекторе | выключено |
| Автолок при первой правке | выключен |
| Фон превью | тёмный |
| Импорт для превью | по кнопке |
| Миниатюры в списках файлов | только картинки |
| Лимит места превью | 1024 МБ |

## Учётные данные для push

При отказе аутентификации на http(s)-remote открывается окно входа с подсказками для
этого сервера (GitHub, GitLab, Bitbucket): какое имя пользователя вводить и кнопка,
открывающая страницу создания токена. Введённое уходит в `git credential approve` через
stdin и остаётся в хранилище git — пакет его у себя не держит.

Если ssh-remote не принял ключ, пакет проверяет, какой ключ из `~/.ssh` принимает сервер.
Для этого нужны только открытые ключи, пароль не требуется:

* ключ с нестандартным именем файла, который ssh сам не предлагает, добавляется в
  ssh-agent на время сессии редактора;
* для ключа с паролем пакет спрашивает пароль и добавляет ключ в агент до закрытия Unity.
  Пароль передаётся в `ssh-add` только через окружение этого одного процесса — не в
  аргументах, не в файлах и не в журнале;
* если сервер не принял ни один ключ, окно показывает локальные ключи с отпечатками, чтобы
  сверить их со страницей SSH-ключей сервера, и предлагает переключить remote на HTTP(S).

На Windows пакет использует утилиты OpenSSH из поставки Git for Windows — именно этот ssh
запускает git. Если git настроен на другой ssh (`core.sshCommand`, `GIT_SSH`), проверка не
выполняется. Вывод команд с учётными данными в журнал не попадает.

## Своё превью ассетов

Изменения ассетов показываются так, как ассет выглядит: вкладки «Вид», «Инспектор»,
«Изменения» в окне Git, «История ассета», конфликты, миниатюры. Для своих типов это
настраивается тремя классами из пространства имён `Lev.Git.Preview`. Регистрировать их
не нужно — пакет находит наследников сам (через `TypeCache`) в любой редакторской сборке.

| Класс | Отвечает за | Когда нужен |
|---|---|---|
| `ChangeDescriber<T>` | что изменилось, словами инспектора; откат пунктов | чтобы вместо путей полей были понятные строки |
| `AssetPresenter` | как нарисовать одну версию | чтобы «Вид» показывал ассет, а не только поля |
| `AssetLoader` | как превратить байты версии из git в объекты Unity | только для своих форматов файлов |

Без своих классов ассет тоже виден: YAML-ассеты (ScriptableObject, материалы, анимации),
PNG, JPEG, TGA, звук, префабы и модели пакет читает и описывает сам.

Код описателя, показа и загрузчика — в [английском README](README.md#custom-asset-previews)
и в примере: Package Manager → Git for Unity → Samples → Custom Change Preview.

**Подключение из своего пакета** — редакторская сборка компилируется, только когда Git for Unity установлен:

```json
"references": ["Lev.Git.Editor"],
"defineConstraints": ["LEV_GIT"],
"versionDefines": [{ "name": "ru.lev.unity-git", "expression": "1.0.0-alpha.1", "define": "LEV_GIT" }]
```

## Известные ограничения

* Пункты меню всегда на английском: пути меню Unity компилирует, на ходу их не сменить.
* Несколько возможностей опираются на внутренности Unity: метка git в заголовке
  компонента и инспектор в колонках. Если версия Unity их изменит, возможность
  выключится, остальное продолжит работать; что найдено — видно в отчёте о проблеме.
* Токен API GitLab сохраняется на Windows и на Linux с Secret Service (`secret-tool`).
* **В alpha API ничем не гарантирован.** Публичных типов в сборках много, но для своего кода
  предназначено только описанное в этом README: API расширения превью (`Lev.Git.Preview`) и
  интерфейсы интеграций (`IGitIntegration` и соседние). Оба могут измениться до 1.0.0.
  Остальное — детали реализации, они могут поменяться или исчезнуть в любой версии.

## Устройство

| Сборка | Что внутри |
|---|---|
| `Lev.Git.Editor` | ядро: процессы git, статус, коммит, diff, сцены, история, конфликты, LFS, превью, реестр интеграций, хранилище секретов, перевод, диагностика |

## Разработка

* `Tests~/Pure` — тесты движков без Unity (разбор YAML, семантический diff, трёхстороннее
  слияние, слияние текста, подсветка, перевод, вычистка секретов): `dotnet run -c Release`.
* `Tools~/compile-check.sh` — сборка всех сборок и примера компилятором .NET SDK против
  установленного редактора, без открытия Unity.
* `Tools~/localization.py` — проверка, что у каждой строки интерфейса есть перевод, и сборка `.po`.
